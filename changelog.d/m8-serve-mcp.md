`ei serve mcp` runs the stack's MCP server over stdio, so an MCP host (Claude Desktop, an agent runtime) can start it as a child process and drive runs: `start_pipeline`, `create_run`, `list_runs`, `get_run`, `read_artifact`, `resume_run` and `cancel_run`, over the same database and queue as the API. It needs `EI_DATABASE_URL` and `EI_RABBITMQ_URL` and a migrated database, takes no API key (the host that starts it already holds the stack's credentials), and keeps standard output for the protocol, with JSON logs on standard error. **It does not offer `grant_run` or `deny_run` unless the operator sets `EI_MCP_ALLOW_SPEND=1`**: an agent can start, watch and read a run, but cannot raise its own run's cap, and a run it starts is held to `EI_MCP_MAX_RUN_BUDGET_MICRO_USD` (default five dollars), so it cannot open one with a cap of its own choosing (a limit on how many runs it starts is not built yet); a run that needs more budget shows as `awaiting_consent` and the person answers it with `ei run grant`. `McpApplication` takes the same switch as `allow_spend`, which now defaults to off, and `max_run_budget_micro_usd`. A test starts `ei serve mcp` as a real subprocess and talks to it over stdio (initialize, list the tools, call `get_run` on a seeded run).
