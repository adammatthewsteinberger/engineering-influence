The operator can now put ceilings on spend that hold however a run is started or topped up. `EI_MAX_RUN_BUDGET_MICRO_USD` is the most any one run may be given, at its start and after every grant; `EI_MAX_OUTSTANDING_BUDGET_MICRO_USD` is the most unspent budget all runs may hold together (each unfinished run's cap less what it has spent), so a client that starts many runs, or is granted more again and again, runs out of room instead of out of money. Neither is set by default. A brief or a grant that would break one is refused before anything is saved or queued, with `BUDGET_ABOVE_LIMIT` or `OUTSTANDING_BUDGET_EXCEEDED` (HTTP 422), the same way over the REST API, `ei run create` and `ei run grant`, MCP and ACP; a denial is never held back. The check lives in a new `SpendCeiling` service used by `CreateRun` and `ResolveSpendConsent`. A property test (`tests/unit/services/test_spend_ceiling_property.py`) runs random sequences of starts, requests for more, grants, spending and finishing and shows that no ceiling is ever exceeded. A check and the save that follows it are one locked step, so many requests at once to one API or MCP process cannot each pass against the same total; across separate processes (the API and a command line) each holds its own lock, so there it is a check with a window of a few milliseconds. `ei book create` (your own machine, one run) is not held to it.
