A run's status and its files can now be read from the SDK and over MCP, not only from the REST API and the command line. The SDK (sync and async) gains `get_run(run_id)`, a run's summary with the names of its artifacts, and `get_artifact(run_id, name)`, the bytes of one stored file such as `book/my-book.pdf`. The MCP server, when built with a run reader, gains `get_run` and `read_artifact`: a file is returned as text when it is UTF-8 and as base64 when it is not, and one over 1 MiB is refused with `ARTIFACT_TOO_LARGE` and the address that downloads any size. Every surface agrees with the service: `tests/parity/test_run_read_parity.py` checks the REST API, MCP and both SDK clients against it, including binary files and nested names, and a run or file that is not there.
