The database schema is now owned by Alembic instead of `create_all()`. The migrations ship in the wheel, and a new command, `ei db upgrade`, applies them to `EI_DATABASE_URL` (it needs the `runtime` extra, prints the revision it reached and never prints the connection string). The baseline creates the ledger, outbox, run, journal and artifact tables, and creates only the ones that are missing, so a database made by the earlier `create_all()` is adopted with its rows intact. The API and the worker no longer create tables: they check the revision at start-up and exit with `the database schema is not at the latest revision; run `ei db upgrade``, which removes the race where both created the schema on first start. **Breaking:** the SQL repositories no longer create their tables or default to an in-memory database, so anything that embeds them must run the migrations first, and an existing deployment must run `ei db upgrade` before starting a new release. The compose file gains a one-shot `migrate` service that the API and the worker wait for. A test builds the schema from the migrations and fails if it differs from the SQLModel models, so a model change without a migration fails the build. ADR 0006 exempts `infrastructure/migrations/` from the one-class-per-file rules, because an Alembic script is a module of functions by contract.
