The worker now handles `run.advance` jobs. A new `JobRouter` sends each job to the service for the prefix of its kind, `pipeline.*` to the existing pipeline service and `run.*` to the new `ProcessRunJob`, which checks the payload (`run_id`, `stage` and an `attempt` of at least 1; extra keys such as a correlation id are ignored) and calls `AdvanceRun`. A kind nobody handles is still refused with `UNKNOWN_JOB_KIND` and dead-lettered. `JobOutcome` gains a `run_*` member for every `AdvanceOutcome` (`run_advanced`, `run_completed`, `run_retrying`, `run_parked`, `run_failed`, `run_skipped`, `run_repaired`), so the worker's `jobs.outcome.*` counters distinguish them, and a test fails if an outcome is added without one. The worker opens the run, journal and artifact stores on the same database as the ledger and closes them with it. Until the model adapters arrive, stages run through `DeterministicStageExecutor`, a placeholder that journals a zero-cost entry and stores `<stage>.md` from the brief's idea, in the same way `DeterministicRunner` stands in for pipelines. Nothing creates a run yet, so no `run.advance` job is queued in the compose stack; an end-to-end test runs one through the real handler, router, run advancer and SQL stores.
