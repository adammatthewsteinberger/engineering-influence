The build tools are now limited in memory and disk as well as time. A `ToolLimits` model holds the three ceilings, and `ProcessRunner` checks them every half second: resident memory summed over the tool and everything it started (8 GiB for `latexmk` and `tex4ebook`, 4 GiB for `epubcheck`, 2 GiB for the page renderer; read with `ps`, so a JVM's reserved address space does not count), and the size of the directory it writes into (4 GiB; `epubcheck` writes nothing, so none is measured). A tool over a limit is killed with its whole process tree and the build fails with a `BookBuildError` naming the tool, the limit and its last output. The limits are constructor arguments, not settings, and they are sampled, so a tool can pass one by what it can allocate or write in half a second. The fixture books build byte-identically through the limiting runner (final PDFs, EPUBs, covers and reports), and peak at about 400 MiB. New toolchain tests make real `lualatex` allocate and write past its limits.
